# CLAUDE.md

Ongoing project memory: conventions and decisions made during the build, and gotchas discovered along the way. See PLAN.md for the feature spec and build order.

## Backend (Step 1 — FastAPI skeleton + MongoDB)

- **Structure**: application code lives under `backend/app/`, not directly in `backend/`, so the package (`app`) is importable and `uvicorn app.main:app` works from `backend/` as the working directory.
  - `app/core/` — settings (`config.py`) and the Mongo connection (`database.py`). No `routers/models/schemas` code should read environment variables directly; they import `settings` from `app.core.config`.
  - `app/routers/` — one module per resource, each exposing an `APIRouter`; mounted in `main.py` under `/api/v1`.
  - `app/models/` and `app/schemas/` — currently empty placeholders. Convention going forward: `models/` holds Mongo document shapes (plain dict-oriented helpers, since we're using Motor directly rather than an ODM), `schemas/` holds Pydantic request/response models for the API layer. Keep them separate so API contracts can evolve independently of stored document shape.
- **Settings**: `app/core/config.py` uses `pydantic-settings` (`BaseSettings`), reading from environment variables and an optional `.env` file (`backend/.env`, gitignored — see `.env.example` for the template). Nothing is hardcoded; every setting has a sensible local/docker-compose-friendly default so the app boots without a `.env` file present.
  - `MONGO_URI` defaults to `mongodb://mongo:27017` (the docker-compose service name). Override to `mongodb://localhost:27017` (or similar) for running the backend outside Docker against a local/mapped Mongo.
  - `CORS_ORIGINS` is a comma-separated string (parsed via `settings.cors_origin_list`), defaulting to `http://localhost:3000` for the Next.js dev server.
- **Mongo connection**: uses `motor` (async driver). The client is created/closed in `main.py`'s FastAPI `lifespan` handler (not at import time), so tests/tooling can import `app.main` without opening a socket. `serverSelectionTimeoutMS=5000` is set explicitly — Motor's default is 30s, which made the health check hang for 30 seconds before failing when Mongo was unreachable during local testing. Keep this timeout in place (or tune it) rather than relying on the driver default.
- **Health check**: `GET /api/v1/health` pings Mongo via `admin.command("ping")` and returns `200 {"status": "ok", "mongo": "connected"}` or `503 {"status": "error", "mongo": "unreachable"}`. Verified locally: 503 path against no Mongo, and 200 path against a throwaway `docker run mongo:7` container.
- **requirements.txt** pins exact versions (fastapi, uvicorn[standard], motor, pydantic, pydantic-settings, python-dotenv) rather than ranges, for reproducibility during early development.

## Backend (Step 2 — customer & power source models + CRUD)

- **Schema layering** (`app/schemas/<resource>.py`): each resource gets a `*Base` (shared fields), `*Create(Base)` (identical to `Base` for these two resources — creation requires everything `Base` requires), `*Update` (every field `| None = None`, independent of `Base` so nothing is accidentally required), and `*Response(Base)` (adds `id: str`, the string-serialized Mongo `_id`). Follow this same four-schema shape for the step 3 (auth) and step 4 (scheduling) models.
- **Repository layer** (`app/models/<resource>.py`): all Motor calls live here, never inline in routers. Each module exposes `create_<resource>`, `list_<resource>s`, `get_<resource>`, `update_<resource>`, `delete_<resource>`, taking `db: AsyncIOMotorDatabase` as the first argument (obtained via `Depends(get_database)` in the router) and plain `dict`s in/out — routers convert to/from Pydantic schemas. `app/models/common.py` holds the two bits shared by every resource: `serialize_doc` (`_id` → `id` string) and `to_object_id` (returns `None` on an invalid/malformed id string rather than raising, so callers can uniformly treat "not a valid ObjectId" the same as "not found" and return 404 — an invalid id is never a 400/500 here). Reuse `common.py` for future resources instead of re-deriving this per module.
- **Uniqueness**: `customers.service_account_number` and `power_sources.name` each have a unique index (`ensure_indexes` in `app/models/customer.py` and `app/models/power_source.py` respectively), created from `main.py`'s `lifespan`. `DuplicateKeyError` from Mongo is caught in both the `customers` and `power_sources` routers on create *and* update (not just create) and turned into a 409, since the same unique index can be violated either way. **Superseded by step 5**: these indexes were global at the time this was written; step 5 retrofitted per-client ownership onto both resources and changed both to compound indexes scoped by `client_username` — see that section.
- **`power_sources.name`** is a field *not* in PLAN.md's original power-source field list (power type, instantaneous output, actual output only) — it was added specifically to give power sources a natural unique key, at explicit user request, after PLAN.md step 2 was otherwise already built. Required on create, part of `PowerSourceUpdate` as optional. If PLAN.md is ever revised, reconcile this field there too; for now treat `name` as a real, required field going forward (e.g. step 4's scheduling grid can reference/display it) rather than a throwaway.
- **Money fields**: `payment_history[].amount` and `total_overdue_payment` are plain `float`, rounded to 2 decimal places via a Pydantic `field_validator` (not `Decimal`/BSON `Decimal128`, to avoid the conversion friction that comes with those in a prototype). Revisit if cent-precision correctness ever matters beyond display.
- **Payment date**: `PaymentRecord.date` is typed as `datetime`, not `date` — BSON has no native `date`-only type, and Motor will raise `InvalidDocument` trying to write a bare `datetime.date`. Pydantic v2 happily parses a `"YYYY-MM-DD"` string into a `datetime` at midnight, so the API still accepts date-only input; the type is just `datetime` under the hood so it round-trips through Mongo cleanly.
- **`PowerType` enum** values are the literal strings from PLAN.md, including the ones with spaces (`"natural gas"`, `"waste heat"`) — the API accepts/returns those exact strings, not underscored variants.
- Verified locally end-to-end against a throwaway `docker run mongo` container: create/list/get/update/delete for both resources, 409 on duplicate `service_account_number` and duplicate `name` (create and update paths), 404 for both a malformed id and a well-formed-but-missing id, 422 on an invalid `power_type` and on a missing `name`, and both unique indexes present via `getIndexes()`.

## Backend (Step 3 — client auth: signup/login/JWT)

- **`app/models/client.py`** (collection `clients`) follows the step-2 repository pattern, plus `get_client_by_username` (needed for login lookup). Only `username` and `password_hash` are ever stored — no plaintext password field exists anywhere in the data model. `app/schemas/client.py` deliberately has no schema that both accepts and returns a password: `ClientSignup` takes plaintext `password` as input only; `ClientResponse` has just `id`/`username`, so even if a repository dict leaked extra keys, FastAPI's `response_model` filtering drops anything not declared on the schema (verified locally — the stored `password_hash` never appears in the signup response).
- **Password hashing**: `bcrypt` used directly (`hash_password`/`verify_password` in `app/core/security.py`), not `passlib`. Passlib's bcrypt backend has a known compatibility wart with bcrypt ≥ 4.1 (`AttributeError` reading `__about__`), so this avoids that friction entirely — one less moving part for a prototype.
- **JWT**: `PyJWT` (not `python-jose`), HS256, in `app/core/security.py`. `create_access_token(subject)` puts the client's `username` in the `sub` claim (usernames are unique, so it's a sufficient identifier — no extra DB lookup per request); expiry is `settings.jwt_expiration_hours` (default 24, env `JWT_EXPIRATION_HOURS`), signed with `settings.jwt_secret_key` (env `JWT_SECRET_KEY`, defaults to an obviously-fake local value — **must** be overridden outside local dev, same pattern as other settings defaults).
- **`get_current_client`** (`app/core/security.py`) is the auth dependency: reads `Authorization: Bearer <token>` via FastAPI's `HTTPBearer(auto_error=False)`, verifies signature + expiry, and returns the `sub` (username) string — or raises 401 (`"Not authenticated"` if no token given, `"Invalid or expired token"` if verification fails; both include a `WWW-Authenticate: Bearer` header). It does **not** re-check the DB that the user still exists on every call — a token for a since-deleted client stays valid until it expires. Acceptable for this prototype; revisit if that ever matters.
- **Protecting a router**: add `dependencies=[Depends(get_current_client)]` to the `APIRouter(...)` call itself (see `customers.py`/`power_sources.py`) rather than repeating `Depends(get_current_client)` on every route function — one line protects every route on that router, including ones added later. Use this same pattern for the step 4 scheduling router. If a route ever needs to know *which* client is calling (not just that some valid client is), add `client_username: str = Depends(get_current_client)` as a normal parameter on that specific route instead — the dependency return value is the username either way.
- **Login response** is generic on failure — both a wrong password and a nonexistent username produce the identical `401 {"detail": "Invalid credentials"}` (verified locally), so the API never reveals which part was wrong.
- **Startup index creation** (`main.py` `lifespan`) now creates three indexes (clients, customers, power_sources) and runs them via `asyncio.gather(..., return_exceptions=True)` rather than a sequential loop — sequential awaits made a Mongo-unreachable boot take ~15s (3 × the 5s `serverSelectionTimeoutMS`) before this was caught in local testing; concurrent gather brings that back down to ~5s. Add any future resource's `ensure_indexes` to the same `index_jobs` tuple rather than a separate awaited call.
- **New deps**: `bcrypt==5.0.0`, `PyJWT==2.13.0` added to `requirements.txt`. `JWT_SECRET_KEY` and `JWT_EXPIRATION_HOURS` added to `.env.example` (secret is a clearly-labeled placeholder, not a real value).
- Verified locally end-to-end against a throwaway `docker run mongo` container: signup, duplicate-username signup (409), login with wrong password / nonexistent user (both generic 401), successful login issuing a JWT, `/api/v1/customers` and `/api/v1/power-sources` returning 401 with no token and with a garbage token, 200 with a valid token, unique index on `clients.username` present via `getIndexes()`, and the stored client document confirmed to contain only a bcrypt hash, never plaintext.

## Backend (Step 4 — recurring power scheduling grid)

- **Not week-scoped**: the schedule is a single, static, cyclical template per client — Sunday through Saturday, reused every week. There is **no `week_start_date`, no per-week documents, and no history of past weeks**. An earlier version of this step modeled it as one document per client *per week*; that was wrong and has been fully removed (schema, router paths, and Mongo index). If you see any reference to `week_start_date` anywhere in the schedule code, it's a regression — the correct model is exactly one document per client, period.
- **Document shape** (collection `schedules`, `app/models/schedule.py`): exactly one document per client —
  ```json
  {
    "_id": ObjectId(...),
    "client_username": "alice",
    "grid": { "0": { "9": "<power_source_id>", "10": "<power_source_id>" }, "6": { "23": "<power_source_id>" } }
  }
  ```
  The grid is **sparse** — only assigned slots are present, not a dense 7×24 matrix of nulls — and is looked up by `client_username` alone, never by Mongo `_id` or any date/week key; there's no `GET/PUT /schedules/{id}` route, so `ScheduleResponse` deliberately has no `id` field (a documented deviation from the step-2 four-schema pattern, which fits resources addressed by Mongo `_id`).
- **Day/hour convention** (`app/schemas/schedule.py`): `grid` is `dict[Day, dict[Hour, str]]` where `Day = Annotated[int, Field(ge=0, le=6)]` (**0 = Sunday, 6 = Saturday**) and `Hour = Annotated[int, Field(ge=0, le=23)]`. The frontend scheduling grid (step 8) must use this exact 0=Sunday convention and these exact ranges — out-of-range values are rejected with 422 automatically by Pydantic (verified locally, with a clear per-key error message).
- **Mongo key-type gotcha**: BSON documents only allow string keys — inserting a dict with `int` keys raises `bson.errors.InvalidDocument` (confirmed locally). The API schema uses `int` keys (`0`-`6`, `0`-`23`) per the spec, but the repository's `_grid_to_mongo` converts them to `str` keys before every write. Reads need no inverse conversion: Pydantic v2 automatically coerces the stored `str` keys (`"0"`, `"9"`, ...) back to `int` when the raw Mongo doc is validated against `ScheduleResponse` (also confirmed locally), so the router passes Mongo's `find_one`/`find_one_and_update` result straight through as the response body with no manual reshaping.
- **Existence validation**: before every `PUT`, the router collects the distinct `power_source_id` values referenced anywhere in the incoming grid and calls `power_source_repo.get_power_source` for each; any that don't exist (including malformed-ObjectId strings, which `get_power_source` already treats as "not found") produce `400 {"detail": "Power source with id '<id>' does not exist"}` and nothing is written. This cross-resource check lives in the router, not in either repository module, so `app/models/schedule.py` stays scoped to schedule storage only.
- **Per-client scoping**: `client_username` is taken *only* from `Depends(get_current_client)` (the JWT subject) — never from the request body or a query parameter — for both `GET` and `PUT`. A **single-field** unique index on `client_username` (`ensure_indexes` in `app/models/schedule.py`) guarantees exactly one document per client, ever; `PUT` upserts via `find_one_and_update(..., upsert=True)` keyed on `client_username` alone, so it's impossible for one client's request to read or overwrite another's schedule. Verified locally with two separate clients: independent grids, `db.schedules.countDocuments({})` staying at 1 per client across repeated `PUT`s, confirmed via `db.schedules.find()` that each stored document has no date/week field at all.
- **`PUT` is a full replace, not a merge** — re-`PUT`ing a smaller grid discards the previously-set slots that aren't in the new payload (verified locally); `PUT`ting `{}` (or omitting `grid` entirely, which defaults to `{}`) clears the schedule without deleting the document.
- **`GET` never 404s**: a client with no saved schedule yet gets back `200 {"grid": {}}` rather than 404 — verified locally.
- **Router paths**: `GET /api/v1/schedules` and `PUT /api/v1/schedules` — no path parameter, since there's nothing to key the URL on beyond the caller's own identity.
- **Router auth**: `dependencies=[Depends(get_current_client)]` on the `APIRouter(...)` itself, same as `customers`/`power_sources` (see step 3); each route additionally takes `client_username: str = Depends(get_current_client)` as a normal parameter, since (unlike those two routers) every handler here needs the actual identity, not just proof that *some* valid client is calling.
- **Startup indexes**: `schedules` is a fourth entry in `main.py`'s `index_jobs` tuple (see step 3) — runs concurrently via `asyncio.gather` alongside the other three, so Mongo-unreachable boot time stays ~5s regardless of how many resources are added.
- No new dependencies were needed for this step.

## Backend (Step 5 — mock SOAP meter-reading integration)

- **Retrofitted per-client ownership onto customers and power sources.** Going into this step, `/api/v1/customers` and `/api/v1/power-sources` required a valid JWT but did **not** filter by which client created a record — any authenticated client could see/edit/delete any customer or power source (schedules, from step 4, were the only resource already scoped correctly). This was a real gap against PLAN.md's "each client's list of..." framing, caught while building the meter-reading endpoint (which needed to scope customer lookup to the caller) and corrected immediately, project-wide, at the user's explicit direction — not just patched locally for the new endpoint.
  - Both `app/models/customer.py` and `app/models/power_source.py` now take a `client_username` argument on every read/write function (`list_*`, `get_*`, `update_*`, `delete_*`); `get_*`/`update_*`/`delete_*` filter `{"_id": oid, "client_username": client_username}` together in one query, so a record owned by another client is indistinguishable from a nonexistent one — same "don't leak whether it exists" principle as the malformed-id case in `common.to_object_id`.
  - Both routers now take `client_username: str = Depends(get_current_client)` on every route (not just where previously present) and pass it through; `create_*` stamps the new document with `data["client_username"] = client_username` before inserting. `client_username` is never in the public schemas (`Create`/`Update`/`Response`) — same pattern as `password_hash` on clients — so it never leaks into a response.
  - **Uniqueness moved from global to per-client**: `ensure_indexes` for both resources now creates a *compound* unique index — `(client_username, service_account_number)` for customers, `(client_username, name)` for power sources — replacing the single-field unique indexes from step 2. Two different clients can now legitimately use the same service account number or power source name; the constraint is "unique within one client's own list," not "unique across the whole system." Verified locally: bob successfully created a customer with the exact same `service_account_number` alice already used, and a power source with the same `name` alice already used — both 201s — while a client duplicating *their own* value still gets 409.
  - **Bug found post-step-8, during review**: the user hit exactly the cross-client conflict this bullet says shouldn't happen — a power source name rejected as taken by "a different customer." Root cause: `create_index` never *removes* an old index with a different key spec, so this bullet's own migration (single-field → compound) only ever worked on a freshly created database — every prior test in this file used a throwaway `docker run mongo` container, which never carries the pre-migration index, so the gap was invisible until it hit a real, continuously-running local Mongo that had been alive since step 2. On such a database the old global-unique `name_1` / `service_account_number_1` index was still silently enforced *alongside* the new compound one. Fixed by adding `app.models.common.drop_stale_unique_index(collection, key)` — called from both `ensure_indexes` functions immediately before creating the compound index — which looks up `index_information()` and drops any index whose key spec exactly matches the old single-field shape. This makes `ensure_indexes` self-healing on every startup regardless of the database's history, not just correct on a fresh one. Verified by manually creating the legacy single-field unique indexes on a throwaway Mongo container (simulating a pre-step-5 database), starting the app, confirming both stale indexes were dropped and replaced by the compound ones (`getIndexes()`), and confirming two different clients can now both create a power source/customer with the identical name/account number (201/201) while a client duplicating their own value still correctly gets 409. Also confirmed idempotent: restarting the app a second time against the now-migrated database creates no errors and no duplicate index churn. `schedules` was checked too — its own step-4 index history (week-scoped → single-document-per-client) has the same theoretical stale-index shape, but since the new schema never writes the old `week_start_date` field, any leftover compound index there is dormant rather than a live conflict, so it was left as-is; only `customers` and `power_sources` needed the fix.
  - **Cascading fix**: `app/routers/schedules.py`'s existence check (`power_source_repo.get_power_source(db, power_source_id)`) now passes `client_username` too — a schedule can only ever reference the calling client's *own* power sources, consistent with the new ownership model. Easy to miss since `schedules.py` wasn't itself being changed for this step; check for this kind of cross-router ripple whenever a shared repository function's signature changes.
- **SOAP server library**: `spyne` (2.14.0), the only actively-viable Python SOAP *server* framework left (`zeep`/`suds` are client-only). Spyne is WSGI, not ASGI, so it's mounted into the FastAPI app via `a2wsgi.WSGIMiddleware` (1.10.10) — `app.mount("/soap/meter-reading", WSGIMiddleware(wsgi_app))` in `main.py`. Starlette's own `WSGIMiddleware` was removed from recent versions in favor of `a2wsgi`, so `a2wsgi` is a direct dependency, not incidental. This keeps the mock service in the same process/port as the REST API — no separate service/port to run for local dev — while staying structurally separate (a WSGI sub-app, not an `APIRouter`), per the instruction not to unify SOAP under the REST router style.
- **Mock service** (`app/soap/meter_reading_service.py`): one operation, `GetMeterReading(service_account_number) -> MeterReading{service_account_number, kwh_reading, reading_timestamp}`. No backing store — `_simulate_reading` hashes the account number (`sha256` → seeded `random.Random`) for a **deterministic per-account baseline** (same account always lands in the same realistic 500–5000 kWh range), then adds **unseeded** `random.uniform(-2, 2)` jitter so repeated calls for the same account return slightly different values rather than a frozen constant. Caught in local testing: an earlier version drew *both* the baseline and the jitter from the same seeded `Random` instance, which made the jitter deterministic too — every call returned the byte-identical reading, defeating the point of jitter. Fixed by drawing jitter from the unseeded module-level `random` instead; verified three consecutive calls for one account now return distinct values around the same baseline.
- **WSDL / mount-path gotcha**: `GET /soap/meter-reading?wsdl` (no trailing slash) returns a `307` redirect to `/soap/meter-reading/?wsdl` before serving the WSDL with `200` — this is standard Starlette `Mount` behavior (a request path exactly equal to the mount prefix gets redirected to the trailing-slash form so the sub-app sees a clean root), not a bug. Tried disabling it via `FastAPI(..., redirect_slashes=False)`; that broke the mount entirely (404, since the exact-match-without-slash path then didn't route to the sub-app at all), so it was reverted. Both `curl -L` and `zeep` (via `requests`, which follows redirects by default) handle the redirect transparently — verified the full `zeep.Client(...)` → `GetMeterReading` call working end-to-end through the real running app, not just the WSDL fetch. **To manually check the WSDL**: `curl -L "http://localhost:8000/soap/meter-reading?wsdl"` (the `-L` matters, or you'll just see the 307).
- **SOAP client**: `zeep` (4.3.3), in `app/core/soap_client.py`. Zeep is synchronous (built on `requests`), so `get_meter_reading()` runs it via `asyncio.to_thread(...)` wrapped in `asyncio.wait_for(..., timeout=settings.soap_timeout_seconds)` to avoid blocking the event loop and to bound how long a REST request can hang on a slow/dead SOAP backend. The `zeep.Client` itself is built lazily and cached (`functools.lru_cache`) rather than reconstructed per call, since fetching+parsing the WSDL on every request would be wasteful.
  - `MeterReadingUnavailable` is a single exception type covering timeout, `zeep.exceptions.Error`, and any other failure (connection refused, WSDL fetch failure, etc. — caught via a deliberate broad `except Exception` at this specific integration boundary, since an unhandled exception here must never reach the client as a raw 500). The router (`GET /api/v1/customers/{id}/meter-reading` in `customers.py`) catches it and returns `502 {"detail": "Meter reading service is currently unavailable"}`. Verified locally: pointed a second server instance at an unreachable `SOAP_METER_READING_URL` and confirmed a clean 502 rather than a crash.
  - `settings.soap_meter_reading_url` defaults to `http://localhost:8000/soap/meter-reading` — this is a **self-call**: the app calls back into its own running SOAP mount over HTTP. The default assumes uvicorn is bound to port 8000; override `SOAP_METER_READING_URL` if that's ever not the case (e.g., once Docker networking is introduced in step 9).
- **New endpoint**: `GET /api/v1/customers/{id}/meter-reading` in `app/routers/customers.py` (not a separate router — it's a sub-resource of customers). Auth + ownership follow the same pattern as every other customer route: `client_username` from the JWT, customer lookup scoped to that client, 404 if the customer doesn't exist *or* belongs to someone else. Response schema `MeterReadingResponse` (`app/schemas/meter_reading.py`).
- **New deps**: `spyne==2.14.0`, `a2wsgi==1.10.10`, `zeep==4.3.3` added to `requirements.txt`. `SOAP_METER_READING_URL` and `SOAP_TIMEOUT_SECONDS` added to `.env.example`/`config.py`.
- **How to test manually**: with the server running on port 8000, `curl -L "http://localhost:8000/soap/meter-reading?wsdl"` for the WSDL; sign up/log in via `/api/v1/auth`, create a customer, then `curl http://localhost:8000/api/v1/customers/<id>/meter-reading -H "Authorization: Bearer <token>"` for a live simulated reading.

## Frontend (Step 7 — login/signup pages)

- **Two separate routes, not a toggle page**: `/login` and `/signup`, each a real page (`app/login/page.tsx`, `app/signup/page.tsx`) rather than one component with mode state. Chosen because the step-6 header CTA already linked to `/login` specifically, and separate routes are the more idiomatic App Router shape - bookmarkable/shareable URLs, independent `<title>` metadata, and no conditional-mode branching inside one form component. Both pages share `components/AuthCard.tsx` (page shell: `Header` + centered white card + `Footer`, on the light `--color-bg`) and `components/AuthForm.module.css` (field/button/error styling used by both `LoginForm` and `SignupForm`) so they stay visually identical apart from copy - reuse this same pair for any future auth-adjacent page rather than duplicating card/field CSS.
- **Signup auto-logs in**: `POST /auth/signup` doesn't return a token (see step 3), so `SignupForm` immediately follows a successful signup with a `POST /auth/login` call using the same credentials still held in state, then stores the token and redirects to `/service` - creating an account goes straight into the app rather than dropping the user back at a login form they'd have to fill out again. If that follow-up login call fails for some reason (should be rare - the account was just created), it falls back to redirecting to `/login` rather than leaving the user stuck on a broken state.
- **`/service` is a placeholder redirect target** - it doesn't exist until step 8, so both successful login and successful signup currently redirect into a 404. This is expected and was called out explicitly in the task; verified locally that the redirect itself (URL change + token stored) works correctly even though the destination 404s.
- **Token storage** (`lib/auth.tsx`): a React Context (`AuthProvider`/`useAuth`) backed by `localStorage` under the key `psp_token`, using `useSyncExternalStore` (not `useState` + `useEffect`) to read it - `useEffect` + `setState` on mount is the more obvious approach but trips `eslint-plugin-react-hooks`'s `set-state-in-effect` rule and causes an extra render; `useSyncExternalStore` is the React-recommended primitive for exactly this "sync with a browser-only external store" case and has a clean, explicit SSR fallback (`getServerSnapshot` returns `null`) instead of relying on effect timing. `login()`/`logout()` write to `localStorage` then dispatch a synthetic `psp-auth-change` event on `window` so the *same tab* re-reads the snapshot - the native `storage` event only fires in *other* tabs/windows, which was confirmed while testing (logging out didn't update the current tab's header until this was added).
  - **Chose `localStorage` over a cookie**: simpler for a pure-client setup (no cookie attributes/SameSite/expiry to manage, no need for a Next.js API route to broker an `httpOnly` cookie since the FastAPI backend doesn't set cookies at all) and explicitly allowed by the task's "a cookie or similar." Tradeoffs, accepted for a prototype: readable by any script on the page (XSS risk), not visible to Server Components/middleware so there's no SSR-based route protection (a logged-out visitor can still request `/service`'s HTML - step 8 will need a client-side redirect-if-no-token guard, not a middleware one), and a brief "flash of logged-out header" on every full page load before the mount-time snapshot read resolves (state starts `null` until the first client render commits). None of this matters without shipping real user data, which this prototype doesn't.
- **Error copy is hardcoded by status code, not passed through from the backend**: `LoginForm` shows "Incorrect username or password." only on `err.status === 401`; `SignupForm` shows "That username is already taken." only on `err.status === 409`. Everything else (network failure, 500, unexpected status) falls back to a generic "Something went wrong. Please try again." The backend's actual `detail` text is never displayed directly - keeps the copy fully controlled on the frontend and insulated from backend wording changes, and avoids ever accidentally surfacing a more specific/leaky message than intended.
- **Client-side validation**: native HTML `required` on both inputs (blocks a truly empty submit before any JS runs - verified locally that clicking submit with both fields empty does not hit the network) plus a `trim()` check in the submit handler as a backstop for a whitespace-only username, which `required` alone wouldn't catch (verified locally: three spaces in the username field shows "Enter a username and password." without a network call). No password length/complexity constraints client-side, since the backend doesn't enforce any either - a client-side rule the API doesn't share would just be confusing.
- **Logout mechanism**: `Header.tsx` is now a Client Component (`"use client"`, needed for `useAuth()` and the click handler) that swaps its "Client Login" button for a plain "Logout" button when `token` is non-null; clicking it calls `logout()` then `router.push("/")`. Same nav slot either way, so the header layout doesn't shift between logged-in/out states. Converting `Header` to a Client Component surfaced a latent bug: its "What it does" link was a bare `#capabilities` anchor, which only worked from the home page itself - now that `Header` is shared with `/login`/`/signup` (and eventually `/service`), it's `/#capabilities` so it correctly navigates home-then-scrolls from any page. Also switched that link from a plain `<a>` to `next/link`'s `Link` per `eslint-config-next`'s `no-html-link-for-pages` rule, caught by `npm run lint`.
- No new dependencies were needed for this step - `useSyncExternalStore` and the Context API are both plain React.

## Frontend (Step 8a — service area: customers page)

- **Building step 8 in three reviewed sub-steps**: the user explicitly asked for customers (8a), power sources (8b), and the scheduling grid (8c) to be built and reviewed one at a time rather than all at once. This section covers 8a only - the shared service-area infrastructure (route protection, nav, the authed-fetch hook, modal) built here is meant to be reused as-is for 8b/8c, not re-derived.
- **Routing & layout**: `app/service/layout.tsx` wraps every `/service/*` route in `components/service/ServiceShell.tsx` (auth guard + `ServiceNav`), so route protection and the shared nav are written once and apply to every page under `/service`, present or future - 8b/8c's pages don't need to repeat any of this. `app/service/page.tsx` is a bare server-side `redirect("/service/customers")`, so the existing step-7 `router.push("/service")` calls in `LoginForm`/`SignupForm` didn't need to change; it just forwards to the first tab. `ServiceNav` (`components/service/ServiceNav.tsx`) is a deliberately separate component from the marketing `Header` (different link set - Customers/Power Sources/Schedule instead of the marketing nav) but mirrors its visual structure/CSS class shape and reuses the same tokens, so add new service links there, not to `Header`.
- **Auth guard race condition - found and fixed via testing, not theory**: the first version of `ServiceShell` redirected to `/login` whenever `token === null`, on the assumption that `useSyncExternalStore` (see step 7) always resolves to the true `localStorage` value before any effect can observe the stale SSR placeholder. Actually testing it - a genuine hard navigation straight to `/service/customers` while already logged in - showed this assumption was wrong: the guard fired on the transient `null` and bounced a logged-in user to `/login`. Fixed by adding `isHydrated` to `AuthContext`, using a *second* `useSyncExternalStore` (no-op subscribe, `() => true` client snapshot vs `() => false` server snapshot - the standard trick for an "isHydrated" flag that resolves on the same timeline as any other `useSyncExternalStore` value, deliberately not a `useEffect`+`setState` "mounted" flag, which trips the same lint rule below). The guard now only redirects once `isHydrated && token === null`; before that it renders a plain "Loading…" state. Verified both directions after the fix: hard-reloading `/service/customers` while logged in stays put, and the same URL with no token redirects to `/login`.
- **`react-hooks/set-state-in-effect` hit again, twice more, both resolved without an eslint-disable**: this is the React Compiler-powered lint rule from step 7 (`useSyncExternalStore` was adopted there specifically to avoid it for the localStorage read). It fires on *any* effect that (even indirectly, through a called function) leads to `setState`, not just literal synchronous calls - it doesn't distinguish an awaited async call from a truly-synchronous one.
  - **Initial data fetch on mount**: `useEffect(() => { loadCustomers(); }, [loadCustomers])` calling out to a separately-defined `useCallback` trips it, even though the actual `setCustomers` call happens after an `await`. The fix is the exact pattern from React's own docs for data fetching: define the async function *inline inside the effect* with an `ignore` flag set by the cleanup function, and gate every `setState` call on `!ignore`:
    ```tsx
    useEffect(() => {
      let ignore = false;
      async function initialLoad() {
        try {
          const data = await serviceFetch<T>("/api/v1/...");
          if (!ignore) setData(data);
        } catch {
          if (!ignore) setError("...");
        }
      }
      initialLoad();
      return () => { ignore = true; };
    }, [serviceFetch]);
    ```
    This is now the required shape for every service page's initial load (8b/8c included) - a separately-defined reusable `load*` function (for refetching after a mutation, called from event handlers, which aren't subject to this rule at all) is fine to keep *alongside* this, just don't call it from the mount effect directly.
  - **The `isHydrated` flag** (previous bullet) hits the same rule if written as `useEffect(() => setIsHydrated(true), [])` - the classic "mounted" flag pattern. There's no data-fetching-style fix for this one (it's not synchronizing with an external system, just React's own hydration timing), so it uses the no-op-`useSyncExternalStore` trick instead, which sidesteps the rule entirely rather than suppressing it.
- **`lib/useServiceFetch.ts`**: every service page/component calls the backend through this hook, never `apiFetch` directly. It auto-attaches the stored token (so call sites never pass `token:` themselves) and, on catching a 401 from `ApiError`, calls `logout()` and `router.replace("/login")` before rethrowing - one place handles "the JWT expired/was tampered with mid-session" for the whole service area. Verified locally: forcibly overwriting `localStorage`'s token with a garbage string and dispatching the `psp-auth-change` event (see step 7) triggered `CustomersView`'s mount-effect refetch with the bad token, which 401'd and correctly logged out + redirected - confirms the whole chain end to end, not just each piece in isolation.
- **Repository UI pattern for 8a, reused for 8b**: `components/service/<Resource>View.tsx` (page content: loads the list, owns the create/edit modal's open/closed state, defines the mutation handlers) + `components/service/<Resource>Card.tsx` (one card's display + its own local UI state like delete-confirm) + `components/service/<Resource>FormModal.tsx` (create/edit form, wrapped in the shared `Modal`). Mutations always refetch the full list afterward rather than hand-merging local state - simpler and correctness-obviously-right for a prototype's data volumes, at the cost of an extra round trip per action.
- **Card list, not a table**: customers have 9 fields including a nested array (`payment_history`), which doesn't fit a table cell without truncation or horizontal scroll. Cards (`CustomerCard.module.css`) read far better, especially on mobile, and match the site's established card language (`AuthCard`, `CapabilitiesSection` panels). Revisit this choice for 8b - power sources only have 3 fields, so a table may actually fit better there; don't assume cards are the default for every resource.
- **`payment_history` is edited separately from the main form, not as a dynamic field list inside it**: the Create/Edit modal only covers the scalar fields. Adding/removing a payment is a small inline form directly on `CustomerCard`, sending a *partial* `PUT` with just the recomputed `payment_history` array (append or filter client-side, then `PUT {payment_history: [...]}`- the backend's `CustomerUpdate` only sets fields that are present in the body, so this never touches the other fields). This was a deliberate scope call to keep the main form from needing dynamic add/remove rows; if a future step wants that instead, the backend contract (`PUT` is a partial update) already supports it without changes.
- **Delete confirmation is inline, not a native `confirm()` or a second modal**: clicking Delete swaps the Edit/Delete buttons for "Delete this customer? [Yes, delete] [Cancel]" in place. Avoids the jarring, unstyled native browser dialog and avoids a second modal-on-modal for what's a single yes/no decision. Reuse this exact pattern (`confirmingDelete` local state on the card) for 8b's power source cards.
- **Error copy stays hardcoded by status code**, matching the step-7 convention: 409 on customer create/edit → "A customer with that service account number already exists."; anything else → a generic "Something went wrong. Please try again." The modal stays open with the entered values intact on error (React state isn't cleared), so a duplicate-account-number retry just means fixing one field, not re-typing the whole form.
- **Empty state** (`CustomersView.module.css` `.empty`) is a dashed-border panel with a plain sentence and its own "+ Add Customer" button, not just blank space - reuse this shape for 8b/8c's empty states too.

## Frontend (Step 8c — service area: weekly scheduling grid)

- **The last of the three 8a/8b/8c sub-steps - completes Build Order step 8.** Reused the established service-area infrastructure unchanged (auth guard, `useServiceFetch`, the ignore-flag mount-effect fetch pattern, error-copy-by-status-code convention) and the `POWER_TYPE_COLORS` map built ahead of time in 8b specifically for this page's legend.

Keep the palette and legend as two separate components even though both show colored dots - the palette is "which of *my* sources do I want to paint with" (keyed by `power_source_id`), the legend is "what does each *type*'s color mean" (keyed by `PowerType`); a client can own two sources of the same type, so the palette can't be derived from the legend or vice versa.
- **`lib/schedule.ts`**: `DAYS` (0=Sunday..6=Saturday, matching the backend's `ScheduleGrid` convention exactly - see step 4), `HOURS` (0-23), and the paint-tool types: `ERASER` (a sentinel string, not a valid Mongo ObjectId hex string, so it can never collide with a real `power_source_id`) and `PaintTool = string | typeof ERASER | null`. `lib/types.ts` gained `ScheduleGrid = Record<string, Record<string, string>>` (day → hour → `power_source_id`, sparse) and `Schedule = { grid: ScheduleGrid }` - deliberately plain `Record<string,string>` nesting rather than mirroring the backend's `int`-keyed Pydantic type, since JSON (and therefore every value that ever crosses `fetch`) only ever has string keys anyway; unlike the backend (see step 4's Mongo int/str gotcha), the frontend never needs a keyed-type conversion step in either direction.
- **Interaction model chosen: click-or-drag paint with a selected tool, not per-cell modals or dropdowns.** Select a power source (or Eraser) from the palette, then click a single cell or mouse-down-and-drag across a run of cells to paint them all with that tool in one gesture - this is what makes filling in a whole day or a multi-hour block fast, which a per-cell "click to open a picker" interaction wouldn't be. Implementation (`ScheduleGrid.tsx`): each cell is a `<button>` with `onMouseDown` (paints immediately and sets a local `isPainting` flag), `onMouseEnter` (paints again, but only while `isPainting` is true), and `onClick` (paints once more - redundant with `onMouseDown` for a real mouse click, but it's the *only* path a keyboard user gets, since Enter/Space on a focused button fires `click`, never `mousedown`). Painting the same cell with the same value twice is a harmless no-op, so the deliberate overlap between `onMouseDown` and `onClick` needs no deduplication. `isPainting` is reset via a `window`-level `mouseup` listener (not just on the cell), so a drag that ends outside the grid (or outside the browser window) still stops painting correctly.
- **Toggle-off palette selection**: clicking the already-active palette chip again deselects it (returns the tool to `null`), rather than requiring the Eraser as the only way out of "paint mode." With no tool selected, clicking/dragging cells is inert - `ScheduleGrid` guards `paintCell` on `selectedTool === null` and never calls `onPaint` at all, so an accidental click before choosing a tool can't corrupt anything.
- **Save is an explicit button with a visible dirty indicator, not autosave** - the deliberate choice between the two options the task allowed. Reasoning: `PUT /api/v1/schedules` is a **full-grid replace** (see step 4), and a drag gesture can touch a dozen-plus cells in under a second; autosaving per-cell-change would mean firing a full-grid `PUT` on every single cell during a drag, which is both wasteful and risks requests completing out of order against the same document. Batching the whole editing session into one explicit `Save Schedule` click sends exactly one `PUT` with the final grid state. State is made obvious via a text indicator next to the button (`"Unsaved changes"` in copper when `isDirty`, `"All changes saved"` in steel grey otherwise) plus the button itself being disabled whenever there's nothing new to save (`!isDirty || saving || grid === null`) - both signals agree at every moment, so there's no ambiguity about whether a change has been persisted. `isDirty` is set unconditionally on every paint (including a no-op repaint of an already-correct cell during a drag pass) rather than diffing old vs. new value first - a theoretically-avoidable "unsaved changes" flicker for a redundant paint, accepted as not worth the extra bookkeeping.
- **Grid is kept sparse client-side, matching the backend's stored shape exactly**: `ScheduleView.handlePaint` deletes an hour key when erased and deletes an emptied day object entirely (`if (Object.keys(nextDay).length === 0) delete next[dayKey]`) rather than ever writing `null`/empty placeholders - confirmed via a direct `db.schedules.find()` after saving that the stored document has exactly the assigned slots and nothing else, no dense 7×24 matrix.
- **Empty state gates on power sources, not on an empty grid**: if the client has zero power sources, the page shows the standard dashed-border empty-state panel ("No power sources yet - add a power source before building your weekly schedule") with a link to `/service/power-sources`, and doesn't render the palette/grid/legend at all - there's nothing meaningful to paint with yet. An empty *grid* with power sources already created is a normal, valid state (a fresh client's schedule) and renders the full interactive grid as usual, just with every cell unassigned.
- **Grid layout**: days as rows (`Sun`-`Sat` short labels, sticky-left column so they stay visible while scrolling horizontally), hours 0-23 as columns (sticky-top header row) - chosen over the transposed layout because a wide-and-short grid scrolls better on mobile than a narrow-and-tall one, and reuses the exact `overflow-x: auto` wrapper pattern from 8b's power-sources table. Cells are small (`2.25rem × 2rem`) fixed-size buttons, colored via inline `style={{ backgroundColor: ... }}` from `POWER_TYPE_COLORS[source.power_type]` when assigned, plain `--color-bg` when not. Each cell has both a `title` and an `aria-label` of the form `"<Day> <hour>:00 — assigned to <source name>"` / `"...— unassigned"` for hover/screen-reader clarity, since the cell itself carries no visible text.
- No new dependencies were needed for this step.
- Verified locally end-to-end against a throwaway `docker run mongo` container and the real backend on port 8000, using Playwright's raw `page.mouse` API (not just click) to genuinely exercise the drag path: empty state with zero power sources; click-to-paint a single cell; mouse-down-drag across six cells in one gesture, confirmed all six painted in the correct color; Eraser tool clearing a previously-painted cell; Save persisting correctly (`db.schedules.find()` confirmed the exact sparse shape, string keys, one document, no `week_start_date`); a full page reload after save reloading the identical grid from `GET`; keyboard Tab reaching a grid cell with a visible focus ring and Enter painting it; and the mobile (390px) layout, including confirming the sticky day-label column stays pinned while scrolling the grid horizontally.

## Containerization (Step 9 — docker-compose.yml for local development)

- **`backend/Dockerfile`**: `python:3.11-slim` (matches the version pinned locally throughout this build - see step 1's `requirements.txt`). `requirements.txt` is copied and `pip install`ed *before* `COPY app ./app`, so the dependency-install layer stays cached across rebuilds that only touch application code, not `requirements.txt` itself. No `--reload` on the `uvicorn` entrypoint - this image is the "run it for real" build, not the dev loop (hot reload still comes from running `uvicorn --reload` directly against a venv, per `backend/README.md`). Runs as a non-root `appuser` (`useradd --uid 1000`, then `chown -R` the app directory before `USER appuser`) rather than the image's default root. No compiler/build-essential needed - every pinned dependency (`bcrypt`, `PyJWT`, `spyne`, `a2wsgi`, `zeep`, etc.) has prebuilt manylinux wheels for this base image's glibc/Python 3.11 combination, confirmed by a clean `pip install` with no compilation step in the build log.
- **`frontend/Dockerfile`**: three-stage build (`deps` → `builder` → `runner`), the standard Next.js Docker pattern, not something invented for this project:
  - `deps`: `npm ci` against `package.json`/`package-lock.json` alone (copied before the rest of the source), so this layer is cached unless the lockfile changes.
  - `builder`: copies `deps`'s `node_modules` plus the full source, then `npm run build`. This is the stage that needs `NEXT_PUBLIC_API_URL` (see the dedicated bullet below).
  - `runner`: a fresh `node:22-alpine` stage that copies **only** `public/`, `.next/standalone`, and `.next/static` from `builder` - not the full `node_modules` or source tree. This depends on **`output: "standalone"`** now being set in `next.config.ts`, which makes `next build` trace the actual production dependency graph and emit a minimal self-contained server (`server.js` + just the `node_modules` subset it really needs) into `.next/standalone`; without it there's no standalone output to copy and the runtime stage would need the full `node_modules` instead. Runs as a non-root `nextjs` user (uid 1001, alongside a `nodejs` system group) via `addgroup`/`adduser`, with `COPY --chown=nextjs:nodejs` on the two `.next` copies so the app's own files are owned by the user that runs them, not root.
    - **Alpine `adduser` quirk, verified harmless**: `id nextjs` inside the running container reports the user's primary group as `nogroup`, not `nodejs` - a known quirk of BusyBox `adduser -S` on Alpine when no `-G` is passed (this Dockerfile uses the same two-line `addgroup`/`adduser` recipe as Next.js's own official Docker example, verbatim). This does **not** break anything: the `--chown=nextjs:nodejs` on the `COPY` lines sets file ownership directly at build time regardless of the runtime user's primary-group quirk, and `nextjs` (uid 1001) is still the literal owner of every copied file. Confirmed by actually running the container and completing a full signup → login → `/service` flow through it - not just inspecting `id` output and assuming.
  - `frontend/public/` didn't exist before this step (nothing in the project uses it - the favicon is `app/icon.svg`, an App Router file-convention icon, not a `public/` asset) but the standard runner stage's `COPY --from=builder /app/public ./public` line assumes it exists and errors on a missing source path. Added an empty `frontend/public/.gitkeep` rather than dropping that `COPY` line, so a future static asset can just be dropped into `public/` without anyone needing to remember to also touch the Dockerfile.
- **`NEXT_PUBLIC_API_URL` is a Docker build arg, not a runtime environment variable - this is the crux of step 9's "common point of confusion" callout.** Next.js inlines every `NEXT_PUBLIC_*` variable directly into the client-side JavaScript bundle **at `next build` time** - it is not read from the environment when the container later starts, unlike every other setting in this project (`MONGO_URI`, `JWT_SECRET_KEY`, etc., which the backend reads live via `pydantic-settings`). Concretely:
  - `frontend/Dockerfile`'s `builder` stage declares `ARG NEXT_PUBLIC_API_URL` and `ENV NEXT_PUBLIC_API_URL=$NEXT_PUBLIC_API_URL` immediately before `RUN npm run build` - the value has to be present *during that specific build step*, or it's simply absent from the compiled output forever (setting it on the running container afterward has zero effect - the JS was already generated).
  - `docker-compose.yml` therefore passes it under `frontend.build.args`, not `frontend.environment` - only `build.args` actually reaches the Dockerfile's `ARG` at build time; a plain `environment:` entry would be invisible to the build and the client bundle would fall back to `apiFetch`'s hardcoded `http://localhost:8000` default (see step 6) rather than anything Compose-specific, which happens to work here only by coincidence (see next bullet) - don't rely on that coincidence elsewhere.
  - **The value itself is `http://localhost:8000`, not `http://backend:8000` - and this is the actual point of confusion the task called out.** `apiFetch` (step 6) runs entirely in the *browser*, not inside any container - it's client-side `fetch()`, executed on the developer's own machine after the page loads. The browser has no membership in the Compose network and cannot resolve `backend` as a hostname at all; it can only reach whatever the *host* machine can reach. Since `docker-compose.yml` publishes the backend's port 8000 to the host (`ports: ["8000:8000"]`), `http://localhost:8000` from the browser's perspective correctly reaches the backend container. `http://backend:8000` is the right address for *container-to-container* calls (e.g. what `backend`'s own `SOAP_METER_READING_URL` self-call would use if it were calling a different service instead of itself) but would simply fail to resolve for anything running in the browser. This project has no server-side (Next.js Server Component/Route Handler) calls to the backend to worry about as a second case - every backend call already goes through `useServiceFetch`/`apiFetch` from a Client Component (steps 7/8), so `NEXT_PUBLIC_API_URL=http://localhost:8000` is the complete, correct answer here, not a simplification of a more complex reality.
- **`docker-compose.yml`** (project root): three services, no top-level `version:` key (obsolete in current Compose releases; modern `docker compose` ignores/warns on it).
  - **`mongo`**: official `mongo:7` image (matches the version used in every throwaway-container test throughout this project), a named volume `mongo_data:/data/db` for persistence, and a `healthcheck` (`mongosh --eval "db.adminCommand('ping')"`) so `backend`'s `depends_on: mongo: condition: service_healthy` actually waits for Mongo to be *accepting connections*, not just for the container process to have started - `depends_on` alone only guarantees start order, not readiness. Verified: `docker compose up` shows `mongo-1 Healthy` before `backend-1 Starting` in the log, and a fresh `backend` container connects successfully on its very first health check with no retry/backoff needed.
  - **`backend`**: built from `./backend`, explicitly sets `MONGO_URI: mongodb://mongo:27017` even though that's already `config.py`'s built-in default (see step 1's original note this section extends) - kept explicit in the compose file for clarity/documentation rather than relying silently on a default that happens to match, since a future change to that default wouldn't obviously break Compose otherwise. `JWT_SECRET_KEY` is passed through as `${JWT_SECRET_KEY:-insecure-dev-secret-change-me}` so it's overridable via a shell env var or a root-level `.env` file (Compose's own, separate from `backend/.env`) without editing the compose file itself, consistent with the existing "must be overridden outside local dev" convention. Every other backend setting (`CORS_ORIGINS`, `SOAP_METER_READING_URL`, etc.) is left unset in Compose because its existing default is already correct for this exact topology - no need to restate values that already work.
  - **`frontend`**: built from `./frontend` with the `NEXT_PUBLIC_API_URL` build arg above; `depends_on: [backend]` for start-order only (no health-gating - the Next.js server itself doesn't need the backend up to start serving pages, only individual page loads eventually do).
  - **Ports**: `frontend` → host `3000`, `backend` → host `8000` (both required, per the task). `mongo` → host `27017` **is** exposed (the task left this as an implementer's choice) - chosen because this project's whole testing workflow (see every "Verified locally" note throughout this file) leans on connecting a host-side `mongosh`/Compass/driver directly to inspect data, indexes, etc., and losing that ability when switching from a throwaway container to Compose would be a regression in debuggability. Revisit for `docker-stack.yml` (step 10) - a production-style deployment is a reasonable place to *not* expose Mongo externally, unlike this local-dev file.
  - All three services set `restart: unless-stopped` - a reasonable default for a local-dev stack that should survive a Docker Desktop restart without manual intervention.
- **`.dockerignore`** in both `backend/` and `frontend/`: excludes the local virtualenv/`node_modules` (each image installs its own inside the build, and copying the host's in - especially `node_modules`, which can contain host-platform-specific native binaries - would be both wasteful and potentially broken on a different image platform), `.env`/`.env.local` (secrets and local overrides have no business inside a built image; runtime config comes from Compose's `environment:` block instead), build output (`.next/`), and VCS/tooling files (`.git/`, `README.md`, the Dockerfile itself). The frontend's `.dockerignore` excluding `node_modules/` is what makes the builder stage's `COPY . .` safe after the `deps` stage's own `COPY --from=deps /app/node_modules` - without it, the host's `node_modules` would land on top of the freshly-installed one.
- **Verified end-to-end, not just "it builds"**: `docker compose build` (~50s cold, mostly `npm ci`), then `docker compose up -d` with mongo's healthcheck gating backend's start; confirmed via `docker exec ... grep -rl localhost:8000 .next/static` that the build-arg actually landed in the compiled client JS (not just present in the Dockerfile); ran a real signup → auto-login → redirect-to-`/service/customers` flow through a live browser against `localhost:3000`, confirming the full browser → frontend container → backend container → mongo container path works, not just each hop in isolation; confirmed both containers run as their non-root users via `id`; and confirmed the named volume actually persists data - created a client, ran `docker compose down` (containers + network removed, volume intentionally left alone), `docker compose up` again, and the client was still present in `mongo`'s data. Mongo's host port was temporarily remapped to `27019` for this test only, since port `27017` was already bound by an unrelated pre-existing local Mongo container on this machine - the committed file uses `27017` as specified.
- No changes to backend or frontend application code were needed for containerization itself, beyond `next.config.ts`'s new `output: "standalone"` line - confirmed `npm run lint`/`npm run build` still pass cleanly outside Docker too, so this is additive, not a trade-off against the existing local-dev workflow.

## Containerization (Step 10 — docker-stack.yml for Docker Swarm + nginx reverse proxy)

- **`nginx/default.conf`**: a single `server { listen 80; ... }` block, not a full replacement `nginx.conf` - the official `nginx:1.27-alpine` image's own top-level `nginx.conf` already sets up sane defaults (worker processes, mime types, gzip, and an `include /etc/nginx/conf.d/*.conf;`) and there was no reason to duplicate or override any of that just to add routing rules. Three `location` blocks, in order:
  - `location /api/` → `proxy_pass http://backend:8000;` - the REST API (step 1 on).
  - `location /soap/` → `proxy_pass http://backend:8000;` - the mock SOAP meter-reading service (step 5), which is mounted on the *same* backend app under `/soap/meter-reading`, not a separate service; both API and SOAP traffic go to the one `backend` service, just on different paths.
  - `location /` → `proxy_pass http://frontend:3000;` - everything else, i.e. the Next.js app.
  - **Deliberately no trailing slash on any `proxy_pass` target** (`http://backend:8000`, not `http://backend:8000/`). This is the one nginx detail that's easy to get backwards and silently break routing: a `proxy_pass` *with* a URI component (even a bare trailing `/`) makes nginx replace the matched `location` prefix with that URI before forwarding - e.g. `/api/v1/customers` would arrive at the backend as `/v1/customers`, stripping the `/api` prefix the FastAPI app actually expects (every router is mounted under `prefix="/api/v1"` - see step 1). Without a URI component, nginx forwards the client's original request URI completely unchanged, so `/api/v1/customers` reaches the backend as `/api/v1/customers`, matching what it's already listening for. Verified directly, not just reasoned through: hit `http://localhost/api/v1/health`, `http://localhost/soap/meter-reading?wsdl`, and `http://localhost/` through a live deployed stack and confirmed all three routed to the right service with the full path intact.
  - **No `resolver`/dynamic-upstream trickery needed for replica scaling, and this was deliberately verified rather than assumed.** The classic "nginx caches Docker DNS and breaks when a container's IP changes" gotcha applies to plain Docker networks (bridge) or Swarm's `dnsrr` endpoint mode, where a service name resolves to individual, changing container IPs. This project uses Swarm's *default* endpoint mode instead, where a service name resolves to one stable virtual IP for the whole service that Swarm's own routing mesh load-balances across every replica behind it - scaling replicas up or down never changes that VIP. Confirmed by actually scaling `backend` from 1 to 3 replicas on a live deployed stack and re-hitting `http://localhost/api/v1/health` repeatedly with zero nginx config changes, zero reload, and no dropped requests.
- **No nginx Dockerfile - the official `nginx:1.27-alpine` image is referenced directly in `docker-stack.yml`, and the config is injected via a Swarm `config` object instead.** The task allowed either approach ("a Dockerfile... or reference the official image directly with a mounted/copied config, your choice"). Chose the config-object route because it's the more genuinely Swarm-native realization of "mounted config" - a host bind-mount doesn't reliably work for a Swarm service that could be scheduled onto any cluster node, whereas a `configs:` entry (`nginx_conf: file: ./nginx/default.conf` at the top level, referenced from the `nginx` service) is cluster-native and content-addressed: change `nginx/default.conf` and redeploy, and Swarm detects the content changed and does a rolling update of just the nginx service, with no image to rebuild or tag to bump. This also means nginx is the only one of the four services in `docker-stack.yml` that never needs a `docker build` step at all.
- **`NEXT_PUBLIC_API_URL` gets a second, different answer here than step 9's** - this is the crux of what step 10 changes, not an afterthought. Step 9's Compose topology has the browser talking to the backend *directly* on a separately-published host port, so `NEXT_PUBLIC_API_URL=http://localhost:8000` was correct there. Step 10 puts nginx in front of *everything* as the single entry point - the backend's own container port is never published to the host at all anymore (`backend` has no `ports:` in `docker-stack.yml`, only `nginx` does) - so `http://localhost:8000` would simply fail to connect from a step-10 deployment; there is no host port 8000 to reach. The correct value for this topology is `NEXT_PUBLIC_API_URL=""` (an empty string), which makes `apiFetch`'s `` `${API_URL}${path}` `` (step 6) collapse to just `path` - e.g. `/api/v1/customers` - a same-origin *relative* URL that the browser resolves against whatever address it actually loaded the page from (`http://localhost/`, or a real domain once this is deployed somewhere with one). This is also why the empty-string build arg works correctly with the existing `API_URL = process.env.NEXT_PUBLIC_API_URL ?? "http://localhost:8000"` fallback logic unchanged - `??` only falls back on `null`/`undefined`, not on an empty string, so no code change was needed in `lib/api.ts` itself, only a different value passed in at build time.
  - **A nice side effect, not something that needed fixing**: since every browser call to `/api/*` is now same-origin (same scheme+host+port as the page itself, both served through nginx on port 80), CORS doesn't come into play for the primary path at all - the browser only performs CORS preflight/enforcement for genuinely cross-origin requests. `CORS_ORIGINS` is left at its existing default in `docker-stack.yml` (unset, so `http://localhost:3000`) rather than changed to anything nginx-specific - it's simply unused by the normal browser flow now, and still there only for the case of hitting the backend directly during debugging.
  - **Because the build-time value now genuinely differs between the two topologies, the frontend needs two separately-built images, not one shared between Compose and Swarm.** `docker-compose.yml`'s `frontend` service builds+tags `power-service-frontend:latest` (absolute `http://localhost:8000`, step 9's answer); the Swarm deployment instead builds `power-service-frontend:swarm` (empty string, this section's answer) via a plain `docker build --build-arg NEXT_PUBLIC_API_URL="" -t power-service-frontend:swarm ./frontend`, documented in the root README's Swarm section. Deliberately different tags, not the same `:latest` reused - reusing the Compose-built image for a Swarm deployment would silently bake in the wrong (unreachable, since port 8000 isn't published in Swarm mode) API base URL, and nothing about that mistake would be visible until a browser actually tried to load data. Verified the distinction is real, not just tag bookkeeping: `grep -rl 'localhost:8000' .next/static` inside the `:latest` image finds matches; the same check inside the `:swarm` image finds none, and a `grep` for the relative `/api/v1` path finds it in the `:swarm` image's bundle instead.
  - The **backend** image, by contrast, needed no equivalent split - it has no build-time arguments at all, only runtime env vars/secrets, so `power-service-backend:latest` (built once, however you like - `docker build` or `docker compose build`) is reused as-is by both `docker-compose.yml` and `docker-stack.yml`.
- **Swarm doesn't build images - `docker-stack.yml` uses `image:`, never `build:`, for every service.** `docker stack deploy` only ever pulls/reuses an already-existing image; a `build:` key in a stack file is silently ignored (a real, meaningful difference from `docker compose up --build`, not just a syntax variation). Both `backend` and `frontend` therefore have to be built *beforehand* with a plain `docker build` (documented in the README's Swarm section) rather than letting `docker stack deploy` do it - unlike `docker-compose.yml`, which still uses `build:` (with a matching `image:` tag alongside it) since Compose really does build for you.
- **Secrets**: `JWT_SECRET_KEY` is the only value in this project that actually warrants a Swarm secret - it's the one genuinely sensitive setting (a cryptographic signing key). Mongo has no authentication configured anywhere in this project (no `MONGO_INITDB_ROOT_USERNAME`/`PASSWORD`, consistent with every prior step - a deliberate simplicity choice for a prototype, not an oversight), so there are no Mongo credentials to convert to a secret either; the task's "any Mongo credentials if applicable" genuinely doesn't apply here, and adding Mongo auth now would be a bigger, out-of-scope change to the connection-string handling that nothing else in this build asked for.
  - `docker-stack.yml` declares `secrets: jwt_secret_key: external: true` - it references a secret that must already exist (created via `docker secret create`, documented in the README), rather than embedding a `file:`-sourced secret from something checked into the repo. Swarm mounts it into the `backend` container at `/run/secrets/jwt_secret_key` (the default path for a secret with no custom `target:`) as a read-only file, not an environment variable.
  - **Required an actual backend code change to be consumed at all, not just declared in the stack file** - `app/core/config.py`'s `Settings` previously only ever read `jwt_secret_key` from an env var (via `pydantic-settings`), which a Swarm secret file has no effect on by itself. Added `_read_secret_file(name)` (checks `/run/secrets/<name>`, returns its stripped contents if the file exists, `None` otherwise - always `None` outside Swarm, so this is a pure no-op for local dev/Compose) and a `model_post_init` hook on `Settings` that overwrites `jwt_secret_key` with the secret file's contents whenever one is present, after the normal env-var-driven construction already happened. The env var (`.env`/`docker-compose.yml`'s `${JWT_SECRET_KEY:-insecure-dev-secret-change-me}`) remains the fallback for every topology that doesn't have a mounted Swarm secret - same settings class, same code path, works correctly in both.
  - Verified this is actually wired up end-to-end, not just present: deployed the stack, confirmed `/run/secrets/jwt_secret_key` exists inside the running `backend` container (`docker exec ... ls /run/secrets`), signed up and logged in through nginx to get a real issued JWT, then - using the backend container's own `PyJWT` - confirmed that JWT verifies successfully against the mounted secret file's exact contents and **fails** signature verification against the hardcoded `insecure-dev-secret-change-me` default. Confirms the secret is actually being read and used to sign tokens, not merely mounted and ignored.
- **`docker-stack.yml` structure**: four services (`mongo`, `backend`, `frontend`, `nginx`), one overlay network (`internal`) shared by all of them - no need for extra network segmentation beyond that for a prototype at this scale, since only `backend` ever talks to `mongo` anyway and nothing about sharing one overlay network exposes any service to the host beyond whatever explicitly has a published `ports:` entry.
  - **`nginx` is the only service with `ports:` published to the host** (`80:80`) - `mongo`, `backend`, and `frontend` have none, reachable only by other services over the `internal` overlay network, matching the task's explicit requirement. (Contrast with `docker-compose.yml`, step 9, where `backend`/`frontend`/`mongo` are all published directly, since there's no reverse proxy in that topology to be the sole entry point instead.)
  - **`deploy.replicas` is explicit (`1`) on every service, not omitted** - makes it obvious at a glance where to change it, and `backend`/`frontend` are genuinely safe to scale arbitrarily (stateless, no node-local storage, verified by actually scaling `backend` to 3 replicas - see the nginx bullet above). `mongo` stays at `1` as a hard requirement, not just the prototype default - naively setting `mongo`'s replicas higher wouldn't create a working multi-node database, only multiple independent, unsynchronized single-node Mongo instances all trying to claim the same volume; a real replica set is out of scope for this project.
  - **`mongo` has a `placement.constraints: [node.role == manager]`**, the one service-specific deploy detail beyond replicas/restart policy. A named volume with the default `local` driver lives on whichever node the container happens to land on - it does not migrate with the container if Swarm reschedules it elsewhere, so an unconstrained `mongo` service could get rescheduled onto a different node after a restart and silently come up with an empty database instead of its previous data. Pinning it to a manager node keeps it landing in the same place every time. This is a complete no-op on the common single-node `docker swarm init` setup this README documents (the only node already satisfies `node.role == manager`) and only starts mattering once additional worker nodes are joined - included now anyway since it costs nothing and is the correct thing to do for a real multi-node cluster.
  - **`restart_policy: condition: on-failure`** on every service - the standard Swarm choice for services that should restart if they crash but not endlessly relaunch after an intentional stop/scale-down.
  - **No `depends_on` in `docker-stack.yml`, unlike `docker-compose.yml`** - Swarm does not honor `depends_on` for startup ordering at all (a real Compose/Swarm difference, not an oversight-by-omission here), so including it would just be misleading dead weight. This is fine without any workaround because the backend already tolerates Mongo not being ready yet at boot (see step 3's `asyncio.gather(..., return_exceptions=True)` note) - it logs a warning and keeps running, and Motor's own connection retry succeeds on the first real request once Mongo does come up, regardless of which order Swarm happens to start the four services in.
