# CLAUDE.md

Ongoing project memory: conventions and decisions made during the build, and gotchas discovered along the way. See PLAN.md for the feature spec and build order.

## Backend (Step 1 — FastAPI skeleton + MongoDB)

- **Structure**: application code lives under `backend/app/`, not directly in `backend/`, so the package (`app`) is importable and `uvicorn app.main:app` works from `backend/` as the working directory.
  - `app/core/` — settings (`config.py`) and the Mongo connection (`database.py`). No `routers/models/schemas` code should read environment variables directly; they import `settings` from `app.core.config`.
  - `app/routers/` — one module per resource, each exposing an `APIRouter`; mounted in `main.py` under `/api/v1`.
  - `app/models/` and `app/schemas/` — currently empty placeholders. Convention going forward: `models/` holds Mongo document shapes (plain dict-oriented helpers, since we're using Motor directly rather than an ODM), `schemas/` holds Pydantic request/response models for the API layer. Keep them separate so API contracts can evolve independently of stored document shape.
- **Settings**: `app/core/config.py` uses `pydantic-settings` (`BaseSettings`), reading from environment variables and an optional `.env` file (`backend/.env`, gitignored — see `.env.example` for the template). Nothing is hardcoded; every setting has a sensible local/docker-compose-friendly default so the app boots without a `.env` file present.
  - `MONGO_URI` defaults to `mongodb://mongo:27017` (the docker-compose service name). Override to `mongodb://localhost:27017` (or similar) for running the backend outside Docker against a local/mapped Mongo.
  - `CORS_ORIGINS` is a comma-separated string (parsed via `settings.cors_origin_list`), defaulting to `http://localhost:3000` for the Next.js dev server.
- **Mongo connection**: uses `motor` (async driver). The client is created/closed in `main.py`'s FastAPI `lifespan` handler (not at import time), so tests/tooling can import `app.main` without opening a socket. `serverSelectionTimeoutMS=5000` is set explicitly — Motor's default is 30s, which made the health check hang for 30 seconds before failing when Mongo was unreachable during local testing. Keep this timeout in place (or tune it) rather than relying on the driver default.
- **Health check**: `GET /api/v1/health` pings Mongo via `admin.command("ping")` and returns `200 {"status": "ok", "mongo": "connected"}` or `503 {"status": "error", "mongo": "unreachable"}`. Verified locally: 503 path against no Mongo, and 200 path against a throwaway `docker run mongo:7` container.
- **requirements.txt** pins exact versions (fastapi, uvicorn[standard], motor, pydantic, pydantic-settings, python-dotenv) rather than ranges, for reproducibility during early development.

## Backend (Step 2 — customer & power source models + CRUD)

- **Schema layering** (`app/schemas/<resource>.py`): each resource gets a `*Base` (shared fields), `*Create(Base)` (identical to `Base` for these two resources — creation requires everything `Base` requires), `*Update` (every field `| None = None`, independent of `Base` so nothing is accidentally required), and `*Response(Base)` (adds `id: str`, the string-serialized Mongo `_id`). Follow this same four-schema shape for the step 3 (auth) and step 4 (scheduling) models.
- **Repository layer** (`app/models/<resource>.py`): all Motor calls live here, never inline in routers. Each module exposes `create_<resource>`, `list_<resource>s`, `get_<resource>`, `update_<resource>`, `delete_<resource>`, taking `db: AsyncIOMotorDatabase` as the first argument (obtained via `Depends(get_database)` in the router) and plain `dict`s in/out — routers convert to/from Pydantic schemas. `app/models/common.py` holds the two bits shared by every resource: `serialize_doc` (`_id` → `id` string) and `to_object_id` (returns `None` on an invalid/malformed id string rather than raising, so callers can uniformly treat "not a valid ObjectId" the same as "not found" and return 404 — an invalid id is never a 400/500 here). Reuse `common.py` for future resources instead of re-deriving this per module.
- **Uniqueness**: `customers.service_account_number` and `power_sources.name` each have a unique index (`ensure_indexes` in `app/models/customer.py` and `app/models/power_source.py` respectively), created from `main.py`'s `lifespan`. `DuplicateKeyError` from Mongo is caught in both the `customers` and `power_sources` routers on create *and* update (not just create) and turned into a 409, since the same unique index can be violated either way. **Superseded by step 5**: these indexes were global at the time this was written; step 5 retrofitted per-client ownership onto both resources and changed both to compound indexes scoped by `client_username` — see that section.
- **`power_sources.name`** is a field *not* in PLAN.md's original power-source field list (power type, instantaneous output, actual output only) — it was added specifically to give power sources a natural unique key, at explicit user request, after PLAN.md step 2 was otherwise already built. Required on create, part of `PowerSourceUpdate` as optional. If PLAN.md is ever revised, reconcile this field there too; for now treat `name` as a real, required field going forward (e.g. step 4's scheduling grid can reference/display it) rather than a throwaway.
- **Money fields**: `payment_history[].amount` and `total_overdue_payment` are plain `float`, rounded to 2 decimal places via a Pydantic `field_validator` (not `Decimal`/BSON `Decimal128`, to avoid the conversion friction that comes with those in a prototype). Revisit if cent-precision correctness ever matters beyond display.
- **Payment date**: `PaymentRecord.date` is typed as `datetime`, not `date` — BSON has no native `date`-only type, and Motor will raise `InvalidDocument` trying to write a bare `datetime.date`. Pydantic v2 happily parses a `"YYYY-MM-DD"` string into a `datetime` at midnight, so the API still accepts date-only input; the type is just `datetime` under the hood so it round-trips through Mongo cleanly.
- **`PowerType` enum** values are the literal strings from PLAN.md, including the ones with spaces (`"natural gas"`, `"waste heat"`) — the API accepts/returns those exact strings, not underscored variants.
- Verified locally end-to-end against a throwaway `docker run mongo` container: create/list/get/update/delete for both resources, 409 on duplicate `service_account_number` and duplicate `name` (create and update paths), 404 for both a malformed id and a well-formed-but-missing id, 422 on an invalid `power_type` and on a missing `name`, and both unique indexes present via `getIndexes()`.

## Backend (Step 3 — client auth: signup/login/JWT)

- **`app/models/client.py`** (collection `clients`) follows the step-2 repository pattern, plus `get_client_by_username` (needed for login lookup). Only `username` and `password_hash` are ever stored — no plaintext password field exists anywhere in the data model. `app/schemas/client.py` deliberately has no schema that both accepts and returns a password: `ClientSignup` takes plaintext `password` as input only; `ClientResponse` has just `id`/`username`, so even if a repository dict leaked extra keys, FastAPI's `response_model` filtering drops anything not declared on the schema (verified locally — the stored `password_hash` never appears in the signup response).
- **Password hashing**: `bcrypt` used directly (`hash_password`/`verify_password` in `app/core/security.py`), not `passlib`. Passlib's bcrypt backend has a known compatibility wart with bcrypt ≥ 4.1 (`AttributeError` reading `__about__`), so this avoids that friction entirely — one less moving part for a prototype.
- **JWT**: `PyJWT` (not `python-jose`), HS256, in `app/core/security.py`. `create_access_token(subject)` puts the client's `username` in the `sub` claim (usernames are unique, so it's a sufficient identifier — no extra DB lookup per request); expiry is `settings.jwt_expiration_hours` (default 24, env `JWT_EXPIRATION_HOURS`), signed with `settings.jwt_secret_key` (env `JWT_SECRET_KEY`, defaults to an obviously-fake local value — **must** be overridden outside local dev, same pattern as other settings defaults).
- **`get_current_client`** (`app/core/security.py`) is the auth dependency: reads `Authorization: Bearer <token>` via FastAPI's `HTTPBearer(auto_error=False)`, verifies signature + expiry, and returns the `sub` (username) string — or raises 401 (`"Not authenticated"` if no token given, `"Invalid or expired token"` if verification fails; both include a `WWW-Authenticate: Bearer` header). It does **not** re-check the DB that the user still exists on every call — a token for a since-deleted client stays valid until it expires. Acceptable for this prototype; revisit if that ever matters.
- **Protecting a router**: add `dependencies=[Depends(get_current_client)]` to the `APIRouter(...)` call itself (see `customers.py`/`power_sources.py`) rather than repeating `Depends(get_current_client)` on every route function — one line protects every route on that router, including ones added later. Use this same pattern for the step 4 scheduling router. If a route ever needs to know *which* client is calling (not just that some valid client is), add `client_username: str = Depends(get_current_client)` as a normal parameter on that specific route instead — the dependency return value is the username either way.
- **Login response** is generic on failure — both a wrong password and a nonexistent username produce the identical `401 {"detail": "Invalid credentials"}` (verified locally), so the API never reveals which part was wrong.
- **Startup index creation** (`main.py` `lifespan`) now creates three indexes (clients, customers, power_sources) and runs them via `asyncio.gather(..., return_exceptions=True)` rather than a sequential loop — sequential awaits made a Mongo-unreachable boot take ~15s (3 × the 5s `serverSelectionTimeoutMS`) before this was caught in local testing; concurrent gather brings that back down to ~5s. Add any future resource's `ensure_indexes` to the same `index_jobs` tuple rather than a separate awaited call.
- **New deps**: `bcrypt==5.0.0`, `PyJWT==2.13.0` added to `requirements.txt`. `JWT_SECRET_KEY` and `JWT_EXPIRATION_HOURS` added to `.env.example` (secret is a clearly-labeled placeholder, not a real value).
- Verified locally end-to-end against a throwaway `docker run mongo` container: signup, duplicate-username signup (409), login with wrong password / nonexistent user (both generic 401), successful login issuing a JWT, `/api/v1/customers` and `/api/v1/power-sources` returning 401 with no token and with a garbage token, 200 with a valid token, unique index on `clients.username` present via `getIndexes()`, and the stored client document confirmed to contain only a bcrypt hash, never plaintext.

## Backend (Step 4 — recurring power scheduling grid)

- **Not week-scoped**: the schedule is a single, static, cyclical template per client — Sunday through Saturday, reused every week. There is **no `week_start_date`, no per-week documents, and no history of past weeks**. An earlier version of this step modeled it as one document per client *per week*; that was wrong and has been fully removed (schema, router paths, and Mongo index). If you see any reference to `week_start_date` anywhere in the schedule code, it's a regression — the correct model is exactly one document per client, period.
- **Document shape** (collection `schedules`, `app/models/schedule.py`): exactly one document per client —
  ```json
  {
    "_id": ObjectId(...),
    "client_username": "alice",
    "grid": { "0": { "9": "<power_source_id>", "10": "<power_source_id>" }, "6": { "23": "<power_source_id>" } }
  }
  ```
  The grid is **sparse** — only assigned slots are present, not a dense 7×24 matrix of nulls — and is looked up by `client_username` alone, never by Mongo `_id` or any date/week key; there's no `GET/PUT /schedules/{id}` route, so `ScheduleResponse` deliberately has no `id` field (a documented deviation from the step-2 four-schema pattern, which fits resources addressed by Mongo `_id`).
- **Day/hour convention** (`app/schemas/schedule.py`): `grid` is `dict[Day, dict[Hour, str]]` where `Day = Annotated[int, Field(ge=0, le=6)]` (**0 = Sunday, 6 = Saturday**) and `Hour = Annotated[int, Field(ge=0, le=23)]`. The frontend scheduling grid (step 8) must use this exact 0=Sunday convention and these exact ranges — out-of-range values are rejected with 422 automatically by Pydantic (verified locally, with a clear per-key error message).
- **Mongo key-type gotcha**: BSON documents only allow string keys — inserting a dict with `int` keys raises `bson.errors.InvalidDocument` (confirmed locally). The API schema uses `int` keys (`0`-`6`, `0`-`23`) per the spec, but the repository's `_grid_to_mongo` converts them to `str` keys before every write. Reads need no inverse conversion: Pydantic v2 automatically coerces the stored `str` keys (`"0"`, `"9"`, ...) back to `int` when the raw Mongo doc is validated against `ScheduleResponse` (also confirmed locally), so the router passes Mongo's `find_one`/`find_one_and_update` result straight through as the response body with no manual reshaping.
- **Existence validation**: before every `PUT`, the router collects the distinct `power_source_id` values referenced anywhere in the incoming grid and calls `power_source_repo.get_power_source` for each; any that don't exist (including malformed-ObjectId strings, which `get_power_source` already treats as "not found") produce `400 {"detail": "Power source with id '<id>' does not exist"}` and nothing is written. This cross-resource check lives in the router, not in either repository module, so `app/models/schedule.py` stays scoped to schedule storage only.
- **Per-client scoping**: `client_username` is taken *only* from `Depends(get_current_client)` (the JWT subject) — never from the request body or a query parameter — for both `GET` and `PUT`. A **single-field** unique index on `client_username` (`ensure_indexes` in `app/models/schedule.py`) guarantees exactly one document per client, ever; `PUT` upserts via `find_one_and_update(..., upsert=True)` keyed on `client_username` alone, so it's impossible for one client's request to read or overwrite another's schedule. Verified locally with two separate clients: independent grids, `db.schedules.countDocuments({})` staying at 1 per client across repeated `PUT`s, confirmed via `db.schedules.find()` that each stored document has no date/week field at all.
- **`PUT` is a full replace, not a merge** — re-`PUT`ing a smaller grid discards the previously-set slots that aren't in the new payload (verified locally); `PUT`ting `{}` (or omitting `grid` entirely, which defaults to `{}`) clears the schedule without deleting the document.
- **`GET` never 404s**: a client with no saved schedule yet gets back `200 {"grid": {}}` rather than 404 — verified locally.
- **Router paths**: `GET /api/v1/schedules` and `PUT /api/v1/schedules` — no path parameter, since there's nothing to key the URL on beyond the caller's own identity.
- **Router auth**: `dependencies=[Depends(get_current_client)]` on the `APIRouter(...)` itself, same as `customers`/`power_sources` (see step 3); each route additionally takes `client_username: str = Depends(get_current_client)` as a normal parameter, since (unlike those two routers) every handler here needs the actual identity, not just proof that *some* valid client is calling.
- **Startup indexes**: `schedules` is a fourth entry in `main.py`'s `index_jobs` tuple (see step 3) — runs concurrently via `asyncio.gather` alongside the other three, so Mongo-unreachable boot time stays ~5s regardless of how many resources are added.
- No new dependencies were needed for this step.

## Backend (Step 5 — mock SOAP meter-reading integration)

- **Retrofitted per-client ownership onto customers and power sources.** Going into this step, `/api/v1/customers` and `/api/v1/power-sources` required a valid JWT but did **not** filter by which client created a record — any authenticated client could see/edit/delete any customer or power source (schedules, from step 4, were the only resource already scoped correctly). This was a real gap against PLAN.md's "each client's list of..." framing, caught while building the meter-reading endpoint (which needed to scope customer lookup to the caller) and corrected immediately, project-wide, at the user's explicit direction — not just patched locally for the new endpoint.
  - Both `app/models/customer.py` and `app/models/power_source.py` now take a `client_username` argument on every read/write function (`list_*`, `get_*`, `update_*`, `delete_*`); `get_*`/`update_*`/`delete_*` filter `{"_id": oid, "client_username": client_username}` together in one query, so a record owned by another client is indistinguishable from a nonexistent one — same "don't leak whether it exists" principle as the malformed-id case in `common.to_object_id`.
  - Both routers now take `client_username: str = Depends(get_current_client)` on every route (not just where previously present) and pass it through; `create_*` stamps the new document with `data["client_username"] = client_username` before inserting. `client_username` is never in the public schemas (`Create`/`Update`/`Response`) — same pattern as `password_hash` on clients — so it never leaks into a response.
  - **Uniqueness moved from global to per-client**: `ensure_indexes` for both resources now creates a *compound* unique index — `(client_username, service_account_number)` for customers, `(client_username, name)` for power sources — replacing the single-field unique indexes from step 2. Two different clients can now legitimately use the same service account number or power source name; the constraint is "unique within one client's own list," not "unique across the whole system." Verified locally: bob successfully created a customer with the exact same `service_account_number` alice already used, and a power source with the same `name` alice already used — both 201s — while a client duplicating *their own* value still gets 409.
  - **Cascading fix**: `app/routers/schedules.py`'s existence check (`power_source_repo.get_power_source(db, power_source_id)`) now passes `client_username` too — a schedule can only ever reference the calling client's *own* power sources, consistent with the new ownership model. Easy to miss since `schedules.py` wasn't itself being changed for this step; check for this kind of cross-router ripple whenever a shared repository function's signature changes.
- **SOAP server library**: `spyne` (2.14.0), the only actively-viable Python SOAP *server* framework left (`zeep`/`suds` are client-only). Spyne is WSGI, not ASGI, so it's mounted into the FastAPI app via `a2wsgi.WSGIMiddleware` (1.10.10) — `app.mount("/soap/meter-reading", WSGIMiddleware(wsgi_app))` in `main.py`. Starlette's own `WSGIMiddleware` was removed from recent versions in favor of `a2wsgi`, so `a2wsgi` is a direct dependency, not incidental. This keeps the mock service in the same process/port as the REST API — no separate service/port to run for local dev — while staying structurally separate (a WSGI sub-app, not an `APIRouter`), per the instruction not to unify SOAP under the REST router style.
- **Mock service** (`app/soap/meter_reading_service.py`): one operation, `GetMeterReading(service_account_number) -> MeterReading{service_account_number, kwh_reading, reading_timestamp}`. No backing store — `_simulate_reading` hashes the account number (`sha256` → seeded `random.Random`) for a **deterministic per-account baseline** (same account always lands in the same realistic 500–5000 kWh range), then adds **unseeded** `random.uniform(-2, 2)` jitter so repeated calls for the same account return slightly different values rather than a frozen constant. Caught in local testing: an earlier version drew *both* the baseline and the jitter from the same seeded `Random` instance, which made the jitter deterministic too — every call returned the byte-identical reading, defeating the point of jitter. Fixed by drawing jitter from the unseeded module-level `random` instead; verified three consecutive calls for one account now return distinct values around the same baseline.
- **WSDL / mount-path gotcha**: `GET /soap/meter-reading?wsdl` (no trailing slash) returns a `307` redirect to `/soap/meter-reading/?wsdl` before serving the WSDL with `200` — this is standard Starlette `Mount` behavior (a request path exactly equal to the mount prefix gets redirected to the trailing-slash form so the sub-app sees a clean root), not a bug. Tried disabling it via `FastAPI(..., redirect_slashes=False)`; that broke the mount entirely (404, since the exact-match-without-slash path then didn't route to the sub-app at all), so it was reverted. Both `curl -L` and `zeep` (via `requests`, which follows redirects by default) handle the redirect transparently — verified the full `zeep.Client(...)` → `GetMeterReading` call working end-to-end through the real running app, not just the WSDL fetch. **To manually check the WSDL**: `curl -L "http://localhost:8000/soap/meter-reading?wsdl"` (the `-L` matters, or you'll just see the 307).
- **SOAP client**: `zeep` (4.3.3), in `app/core/soap_client.py`. Zeep is synchronous (built on `requests`), so `get_meter_reading()` runs it via `asyncio.to_thread(...)` wrapped in `asyncio.wait_for(..., timeout=settings.soap_timeout_seconds)` to avoid blocking the event loop and to bound how long a REST request can hang on a slow/dead SOAP backend. The `zeep.Client` itself is built lazily and cached (`functools.lru_cache`) rather than reconstructed per call, since fetching+parsing the WSDL on every request would be wasteful.
  - `MeterReadingUnavailable` is a single exception type covering timeout, `zeep.exceptions.Error`, and any other failure (connection refused, WSDL fetch failure, etc. — caught via a deliberate broad `except Exception` at this specific integration boundary, since an unhandled exception here must never reach the client as a raw 500). The router (`GET /api/v1/customers/{id}/meter-reading` in `customers.py`) catches it and returns `502 {"detail": "Meter reading service is currently unavailable"}`. Verified locally: pointed a second server instance at an unreachable `SOAP_METER_READING_URL` and confirmed a clean 502 rather than a crash.
  - `settings.soap_meter_reading_url` defaults to `http://localhost:8000/soap/meter-reading` — this is a **self-call**: the app calls back into its own running SOAP mount over HTTP. The default assumes uvicorn is bound to port 8000; override `SOAP_METER_READING_URL` if that's ever not the case (e.g., once Docker networking is introduced in step 9).
- **New endpoint**: `GET /api/v1/customers/{id}/meter-reading` in `app/routers/customers.py` (not a separate router — it's a sub-resource of customers). Auth + ownership follow the same pattern as every other customer route: `client_username` from the JWT, customer lookup scoped to that client, 404 if the customer doesn't exist *or* belongs to someone else. Response schema `MeterReadingResponse` (`app/schemas/meter_reading.py`).
- **New deps**: `spyne==2.14.0`, `a2wsgi==1.10.10`, `zeep==4.3.3` added to `requirements.txt`. `SOAP_METER_READING_URL` and `SOAP_TIMEOUT_SECONDS` added to `.env.example`/`config.py`.
- **How to test manually**: with the server running on port 8000, `curl -L "http://localhost:8000/soap/meter-reading?wsdl"` for the WSDL; sign up/log in via `/api/v1/auth`, create a customer, then `curl http://localhost:8000/api/v1/customers/<id>/meter-reading -H "Authorization: Bearer <token>"` for a live simulated reading.

## Conventions carried forward from PLAN.md

- REST endpoints: `/api/v1/<resource>`, JSON bodies.
- "Client" = logged-in site user; "Customer" = a utility customer managed by a client. Don't conflate these in code (e.g. don't name a client-related collection/model `customers`).
